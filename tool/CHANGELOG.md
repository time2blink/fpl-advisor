## v1.21 — Прошлые сезоны игроков: блок в карточке и якорь в xP (25.10.2026)
Причина: в начале сезона у игрока мало матчей, форма и очки за игру шумят; у вернувшихся из травмы их почти нет. FPL отдаёт итоги прошлых сезонов (`history_past`) в тех же ответах `element-summary`, лишних запросов нет.
- **Новый модуль `seasons.py`**, таблица `player_season` (очки, минуты, старты, голы, ассисты, «сухие», бонус, xG/xA, цена в начале и конце сезона; у 301 игрока, 1339 строк).
- **xP с якорем:** очки и форма смешиваются с прошлым сезоном (последние два, веса 0.6/0.4, очки за 90 → очки за выход) с весом `K/(n+K)`, где n — выходов на поле в этом сезоне. `config.json → prior_k` (по умолчанию 4; 0 — выключить). Только для xP: «Форма» и «Очки за игру» в таблицах остаются фактами. Игроки без надёжной истории (меньше 900 минут за два сезона) считаются по прежней формуле.
- **K выбран бэктестом** (ретро, туры 4–7): без якоря MAE 2.333, корреляция порядка 0.301, топ-10 по позиции 4.22 очка; K=3–6 — MAE 2.31, 0.309, 4.28; K=10–16 хуже. Выигрыш небольшой, но в нужную сторону; оценка шумная (4 тура). Вес прошлого сезона у основных игроков сейчас ~0.35–0.4 и падает с каждым туром.
- **Карточка игрока (Дизайн 2):** блок «Прошлые сезоны» (до 3 сезонов: очки, минуты, старты, Г+А, очки/90, цена), вывод словами, пометка при скачке цены от 2.0 (роль или клуб могли поменяться; вес не меняется), у новичков — «Нет данных АПЛ…». К плитке «xP ближайший тур» добавляется «· прошлый сезон N%», если вес от 10%.
- Бэктест: карточка «Точность прогноза» и brief показывают обе версии xP (без якоря и с якорем).
- Не сделано (по решению: по мере необходимости): вид «Прошлый сезон» в таблице «Игроки», строка в скаут-листе и «Трансферах», шторка в мобильном приложении, Дизайн 1.

## v1.20 — Бэктест точности, журнал событий, надёжное хранение истории (25.10.2026)
Причина: решения стоят на xP, а точность xP никто не измерял; цены и флаги травм менялись незамеченными между дневными снимками; история в кэше GitHub Actions могла потеряться. Этап 0 плана развития (`references/feature-catalog.md`).
- **Новый модуль `backtest.py`.** «Ретро»: для каждого сыгранного тура (с 4-го) прогноз пересчитывается только по данным ДО тура и сверяется с фактом; сравниваются среднее очков, среднее × минуты и наша xP (MAE, корреляция, корреляция порядка, средние очки топ-10 по позиции). «Журнал»: таблица `forecast` пишет xP1 и `ep_next` FPL на ближайший тур (последний до дедлайна) — когда тур сыгран, появится честное сравнение с ep_next. Стартовые цифры (ретро, туры 4–7): наша xP MAE 2.33, корреляция 0.27 — лучше наивных моделей (MAE 2.65 / корр. 0.17 и 2.43 / 0.24), но слабая в абсолюте; цель — xP v2.
- Дизайн 2: карточка «Точность прогноза очков» внизу «Соперников и лиги»; brief: блок «Точность прогноза (бэктест)». Дизайн 1 — позже по просьбе.
- **Новый модуль `eventlog.py`.** При каждом запуске пишет в БД смены цены (`price_event`: было → стало, владение, чистый поток) и смены статуса/шанса/новости (`status_event`). В brief — «События за 48 ч». Основа для калибровки прогноза цен и уведомлений.
- **Хранение истории.** Облачный конвейер публикует `state/fpl.db.gz` (согласованная копия SQLite) вместе с данными; если кэш Actions вытеснен, следующий запуск восстанавливается оттуда, затем из `seed/`. Файлы: `github-check/publish.py`, `.github/workflows/build-data.yml`, `sync.ps1` (+ `backtest.py`, `eventlog.py`).
- **Репозиторий данных.** Решение Жени: данные публичные, секретности нет, важна только защита от записи. Проверено через GitHub API: `fpl-advisor-data` публичный, один коллаборатор (владелец), один deploy key `actions-publish` (запись, нужен конвейеру); исходный `fpl-check` приватный, секрет только `DATA_DEPLOY_KEY`, права workflow по умолчанию «только чтение». Защиту ветки с запретом force-push не включали: конвейер публикует через `push -f`.
- Не сделано: перенос в Дизайн 1; частые снимки игроков (дневной снимок остаётся — по ADR; частые события пишет журнал).

## v1.19.1 — Ручной состав (pending) устаревает сразу после дедлайна своего тура (25.10.2026)
Причина: после дедлайна GW8 программа продолжала брать составы из `config.json → pending` (введены на GW8): у Жени показывалось 0 FT на GW9 вместо 1, а реальные ходы Стаса и Ромы в GW8 были бы не видны. Старая проверка выкидывала `pending` только когда в API появлялись пики на *следующий* тур — то есть через неделю.
- Новое поле `pending.<ключ>.gw` — тур, на который введён состав. Если `gw` ≤ последнего начавшегося тура, блок игнорируется с предупреждением, состав, банк и FT берутся из API.
- Блок без `gw` работает как раньше, но с предупреждением «добавь "gw"».
- `pending` на GW8 очищен: составы всех трёх — из API (у Жени 1 FT, банк £0.0; Рома 2 FT, Стас 3 FT — в GW8 не ходили).

## v1.19 — Шансы по данным FPL: CS %, DC %, голы/ассисты, стандарты, ротация, владение, тур вживую (22.10.2026)
Причина: Женя сравнил с fplukraine.com и попросил сделать всё, что считается по данным API FPL (список — `references/ideas-fplukraine.md`, пункты A1–A8). Сделано в Дизайне 2, «нативно», ничего не ломая; Дизайн 1 — позже по просьбе.
- **Новый модуль `probs.py`** (модель описана в его шапке): по-матчевая история игроков (`player_match`: минуты, старт, xG, xA, xGC, защитные действия) → сила команд (xG/xGA за матч, сглажено к среднему лиги, дом/выезд ×1.12) → для каждого матча: ожидаемые голы команд, **CS %** (Пуассон), у игрока — **CS %** (с шансом 60+ минут), **DC %** (порог 10 у защитника / 12 у остальных, отриц. биномиальное), **гол / 2+ / ассист / гол или ассист**. Ассисты/голы откалиброваны по тому, как их засчитывает FPL в этом сезоне (A/xA ≈ 1.48). Нет истории (`--no-history`) — сила команд из FPL.
- **Стандарты** (пенальти / штрафные / угловые, номер в очереди) — прямо из FPL, по всем игрокам лиги.
- **Владение за 24 ч / 3 дня / 7 дней** — по нашим ежедневным снимкам (3 и 7 дней появятся, когда накопятся снимки).
- **Тур вживую**: `event/{gw}/live` + составы трёх менеджеров — очки с капитаном и хитом, сколько сыграли / играют / ещё сыграют, счёт матчей. Между турами — карточка-заглушка с дедлайном и очками прошлого тура.
- В базе: таблицы `player_match`, `team_snap` (CS %/xG на тур по снимку — для «изменения с прошлого снимка»); кэш live — 60 с.
- **Дизайн 2:**
  - новая вкладка **«Матчи»**: календарь команд на 5/10 туров с переключателем **CS % / xG / xGA / Сложность FPL** (цвет — насыщенность, «у меня N» — сколько моих игроков в клубе), «Тур GWn: сухой матч и голы команд» с изменением, **«Стандарты»** — карточки 20 клубов (пенальти, штрафные, угловые, №1 и №2);
  - «Игроки» → вид **«Шансы на GWn»**: CS %, DC %, гол %, 2+ %, ассист %, Г/А %, xP1, стандарты (П/Ш/У + номер), сортировка по любой колонке;
  - карточка игрока: метки стандартов в шапке, таблица **«Шансы по турам»** (колонки по позиции);
  - «Трансферы»: **«Пары для ротации»** (вратари/защитники, 3/5/8 туров, цена ≤ 4.5/5.0/5.5/любая, «с моими игроками»; «Твоя пара» вратарей первой; только пары, где оба реально играют; игрок — не больше чем в двух парах);
  - «Рынок»: **«Владение: кто набирает»** (Набирают / Теряют, 24 ч / 3 дня / 7 дней);
  - «Соперники»: **«Тур вживую»** сверху и **«Владение в нашей лиге»** (кто у кого, капитаны, «опасный» — сильный игрок у соперника на тур).
- «Календарь команд» (v1.19.1, Женя: «только оттенки зелёного — не информативно»): 5 ступеней цвета как сложность в макете — тёмно-зелёный «лучше всего», светло-зелёный «хорошо», серый «средне», оранжевый «сложно», красный «хуже всего»; границы — по распределению видимых клеток (15/25/25/23/12 %), у «Сложности FPL» — официальная шкала; легенда над таблицей, ступень видна и в подсказке клетки.
- brief: блок «Шансы моих игроков на GWn» (CS/DC/гол/ассист/стандарты).
